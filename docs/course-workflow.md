# 多 Agent 编写、审核与修订流程

## 从零学习的分支边界

`main` 是学习者的工作区。除非明确要求代写实现，不要提前创建后续版本的 `labs/` 或 `tests/` 文件。已有完整实现保存为本地 `reference` 分支，供按需阅读，不自动合并或恢复到 `main`。教程中的代码路径是学习者逐步创建的目标。

以下流程用于教程维护与参考实现验证；需要验证答案时在临时目录或独立工作区进行，不把完整答案预先放入学习工作区。`.agent-runs/` 是历史审核证据，并非入门运行入口。

教程要求学习者运行测试前，必须在正文给出测试文件的创建或追加步骤。只有历史参考测试时，使用可选折叠区并链接 [参考检查说明](reference-checks.md)，同时保留本版独立可运行的直接检查。不能通过仅重分类测试命令来删掉原本承诺的正常、失败和边界行为。

完整范围是路线图中的 40 个模块、196 个检查点。每次分配一组前置条件已满足的模块，
持续推进完整范围；一个批次完成不代表整个项目完成。

## 分工与文件归属

协调者维护环境、共享配置、模块依赖、进度和最终验收。作者负责分配到的模块计划、
教程正文、实验代码及测试；不同作者修改不同目录。审核者独立读取正文和代码，
重放实际示例，只修改审核记录。修订交回作者，避免审核意见与代码修改互相覆盖。

目前最多使用两个并行作者和一个独立审核者，协调者作为第四个 Agent。
依赖同一个前置版本的任务，必须先明确该版本的接口和验证结果。

## 每个版本的完成顺序

1. 细化版本计划：场景、输入输出、不变量、前版缺口、修改目标和验收方法。
2. 作者逐步编写：每步先展示问题，添加一种机制，运行检查，再继续下一步。
3. 作者提供完整当前代码检查点；中间步骤与最终代码保持一致。
4. 独立审核：检查教学连贯性、机制正确性、边界和真实可执行性。
5. 作者逐项修订：记录改动与复测结果；不能靠删除困难验收缩小原目标。
6. 审核者复核：确认问题关闭，重放受影响版本，给出明确结论。
7. 协调者更新已验收状态及证据链接，再安排后续依赖版本。

审核结论使用 `pass / revise / block`。`block` 表示该教程暂不能验收，
不是整个学习项目的暂停状态；可继续修复或推进独立模块。

## 对应技能

- `from-scratch-tutorial-plan`：把单版本目标细化成有前置、验收和代码目标的写作任务。
- `from-scratch-tutorial-build`：逐步自查，每一步运行检查后才能继续。
- `from-scratch-tutorial-review`：检查正文、代码与推导连续性，列出必须修订的问题。
- `workflow-test`：对逻辑先建立失败或对照证据，再实现并验证行为。
- `workflow-build`：保持小步可运行的实现节奏。

独立 Agent 审核是本项目按用户要求增加的流程。技能本身要求逐步检查，
但并不意味着作者自报“测试通过”就已完成独立审核。

## 验证证据

旧版本教程必须从正文中的完整代码在临时目录重放。仅测试仓库中的最新代码，
不能证明 v0、v1 等旧教程仍正确。审核记录注明文档摘要、执行命令、实际输出和限制。
文档或代码变化后，原审核结论不能无条件覆盖新内容。

数据库实验使用实际隔离的数据库实例；网络、崩溃与并发实验注明故障模型。
不允许把跳过、模拟或未执行的测试写成真实数据库验证通过。

当前不自动提交或推送。Git 检查点保存是另一步交付动作，教程可以先通过审核并保留
可重放正文与测试证据，不能虚构尚不存在的 commit 或 tag。
