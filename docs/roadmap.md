# Systems Infra Lab 学习与教程总规划

状态：课程总规划。正文目录见 [教程入口](../tutorials/README.md)，历史作者审核见 [进度记录](progress.md)，当前学习工作区约定见 [从零学习](learning-workspace.md)。

本文件保存在独立的 `systems-infra-lab` 仓库中，作为教程与实验的总路线。
教程目录已经建立；`main` 的实验代码与测试由学习者按版本逐步创建，`reference` 保存此前生成的最终答案。

## 1. 目标与组织方式

采用一个新仓库、10 个知识领域、40 个学习模块。每个模块有自己的
v0–vn；不是 10 个仓库，也不是把 80 个术语各写一篇定义文章。

面向能够编写 Python、使用 Git 和基本 SQL 的开发者。学习目标是：面对一个具体故障，
能够复现、解释内部机制、选择修复办法，并用实验说明代价和适用边界。
开始前补齐进程与线程、文件读写、HTTP、SQL 和基本测试；无需先掌握分布式算法。

用户已经确定的方向：按领域、模块、版本组织，保留复杂概念的工程演进过程。
本计划采用的假设：Python 作为实验主语言，uv 管理 Python 项目，PostgreSQL
作为数据库实验主环境，Docker Compose 管理需要的外部服务。实际版本在首次搭建时固定。

uv 不负责安装 PostgreSQL、编排容器或模拟网络分区。涉及真实数据库行为时，
使用数据库本身；涉及算法推导时，采用小型教学实现。不要用教学实现的结果宣称生产系统可靠。

### 完成一个模块意味着什么

- 有真实场景、最小实验模型、外部输入输出与核心不变量。
- 各版本从已通过检查的前一版本出发，先复现问题，再引入解决问题的机制。
- 每个版本包含文件路径、完整可运行检查点、执行命令、预期输出和失败实验。
- 最终版本能独立重放，并解释正常行为、异常行为、性能权衡与尚未支持的能力。
- 词条只承担导航和速查；原理、代码与故障推导由教程承担。

本计划的全部版本是拟定的能力检查点，不等同于已写好的文章。
如果一个版本在细化时需要同时改变多个机制，应继续拆版本或教程小节；不得为了保留编号压缩推导。

## 4. 领域一：Storage Engines

### S01. 页、记录与访问局部性

覆盖：Data Locality。目标：`labs/storage/pages/`。前置：文件读写。
场景：按订单号读取一百万条订单中的一条。最小模型：固定大小记录、页、文件偏移。
不变量：不同访问布局必须返回相同记录；测量必须标明缓存状态和数据规模。

- v0：逐条扫描记录文件；验收首条、末条、不存在记录，并记录读取字节数。
- v1：为固定长度记录增加直接偏移读取；验证定位正确且不依赖记录位置扫描。
- v2：将读取单位改为页；验证跨页边界，比较单条读取时的额外读取量。
- v3：比较连续与随机访问；固定数据和种子，报告访问次数、页数与延迟分布。
- v4：增加有界页缓存；验证淘汰后仍读对数据，比较冷暖缓存，不把 OS 缓存效果混同为应用缓存效果。

边界：不实现完整缓冲池、并发页锁或写回恢复；不能从 Python 微基准直接推导磁盘硬件结论。

### S02. B-Tree 与页式 B+Tree 索引

覆盖：B-Tree。目标：`labs/storage/bplus_tree/`。前置：S01；磁盘版本需要 S03。
场景：商品按主键查询并按区间翻页。模型：键、页、分隔键、叶子链。
不变量：键有序、叶子同深、父子范围正确、插入后的所有键可检索。
先说明 B-Tree 与 B+Tree 的结构差异，实际编码选择数据库常用的 B+Tree。

- v0：有序数组支持查找和插入；通过移动元素计数展示插入成本。
- v1：构建单叶页索引；明确重复键采用覆盖语义，并检验容量边界。
- v2：实现叶页分裂和新根；验证分裂前后查找与键范围。
- v3：处理内部节点递归分裂；用随机插入与参考字典核对结果及树结构不变量。
- v4：连接叶页实现范围扫描；检查跨叶页、空范围与边界键。
- v5：定义页编码并持久化；关闭后重新打开，验证数据和根页元数据。
- v6：实现删除、借位和合并；验证根收缩，复杂时拆成多个教程步骤。
- v7：汇总运行检查点，对比数组与树的页访问；故障注入明确暴露尚无崩溃原子性的边界。

边界：完成磁盘读写不代表支持崩溃恢复；不实现生产级并发 B+Tree。

### S03. WAL 与崩溃恢复

覆盖：Write-Ahead Logging (WAL)。目标：`labs/storage/wal/`。前置：文件 I/O、基础事务概念。
场景：应用已告诉客户写入成功，但进程突然退出。模型：操作、日志记录、提交记录、数据文件。
不变量：在声明的故障模型内，已确认提交的写入可恢复，未提交写入不得被当作已提交结果。

- v0：直接覆盖数据文件，在更新中间终止进程；复现部分更新。
- v1：定义有长度边界的追加日志格式；验证编码、解码和截断尾记录的识别。
- v2：先写日志再更新数据；验证操作重放，识别只有日志而没有提交标记的更新。
- v3：加入提交记录与恢复规则；检查多个操作作为一个事务恢复或忽略。
- v4：明确 flush、fsync 与返回成功的顺序；用事件轨迹检查顺序，并区分进程退出与断电。
- v5：在每个写入边界注入崩溃，重新启动重放；验证重复恢复不改变逻辑结果。

边界：教学采用简化 redo 模型，不冒充 ARIES；真实断电保证还取决于文件系统和设备。
检查点和安全日志截断在 A02 中展开。

### S04. Bloom Filter 与负查询

覆盖：Bloom Filter。目标：`labs/storage/bloom/`。前置：哈希、概率基础；集成阶段需 S05 v1。
场景：大量不存在的键触发文件读取。模型：位数组、哈希位置、成员判断。
不变量：已插入键无假阴性；“可能存在”必须继续读取真实数据。

- v0：对不存在键逐个查文件，记录负查询读取次数。
- v1：实现位数组与稳定哈希映射；验证插入键始终返回可能存在。
- v2：改变容量、哈希次数和插入量；对比理论与实测假阳性率及内存开销。
- v3：集成到不可变 SSTable 查询前；验证过滤器不改变查询结果并减少负查询 I/O。

边界：普通 Bloom Filter 不支持直接删除；实验不得使用跨进程不稳定的默认字符串 hash 持久化格式。

### S05. LSM、Compaction 与写放大

覆盖：LSM Tree、Compaction、Write Amplification。目标：`labs/storage/lsm/`。前置：S03；过滤器需 S04。
场景：高频更新的事件属性存储。模型：MemTable、SSTable、序列号、删除标记、文件集合。
不变量：读取最新已提交值；合并不得复活已删除数据；文件发布不能出现半成品可见。

- v0：内存有序映射提供 put/get；验证覆盖更新，明确退出即丢失数据。
- v1：刷写不可变 SSTable；验证排序和重启后的单文件读取。
- v2：支持多文件与版本优先级；验证同一键跨文件更新后返回最新值。
- v3：引入删除标记；验证重启后删除仍有效。
- v4：合并文件并处理重复版本；构造旧值残留场景，验证安全保留或回收删除标记。
- v5：加入文件清单和原子发布；在发布前后终止进程，检查旧文件或新文件集合的一致可见性。
- v6：接入 WAL 与 Bloom Filter；分别验证恢复正确性和负查询过滤效果，必要时分两篇教程。
- v7：在同一存储上比较全量与两层 leveled 合并；验证 L1 范围不重叠，测量逻辑字节、SSTable 写字节、查询扫描和保留文件峰值，明确不含 WAL/文件系统放大。

边界：文件发布的崩溃保证需声明目录 fsync 等条件；策略实验不等同于完整 RocksDB。

### S06. 行存、列存与扫描

覆盖：Columnar Storage。目标：`labs/storage/columnar/`。前置：S01。
场景：只查询订单表中的地区与金额。模型：行、列、批次、编码、统计信息。
不变量：行存和列存对相同数据给出相同聚合结果。

- v0：行式布局完成过滤与求和；记录扫描字段和读取字节。
- v1：改为按列存储；同一查询只读取所需列，并核对结果。
- v2：对低基数字段使用字典编码；测量空间，验证解码与缺失值处理。
- v3：增加批次 min/max 数据跳过；验证边界值和统计信息不造成漏读。
- v4：比较扫描、点查和更新负载；解释列存优势的工作负载边界。

边界：不自制完整 Parquet，不把向量化执行与列存本身视为同一个概念。

### S07. MVCC 版本回收与 Vacuum

覆盖：Database Vacuuming。目标：`labs/storage/vacuum/`。前置：T02，PostgreSQL。
场景：频繁更新的表持续膨胀。模型：旧元组版本、活动快照、回收条件、可用空间。
不变量：仍被活动快照需要的版本不可回收。

- v0：持续更新固定行集合；观察逻辑行数与死元组统计的区别。
- v1：执行普通 VACUUM；检查空间可复用，不假定文件立刻缩小。
- v2：保持长事务，再更新并清理；展示旧快照对回收的影响。
- v3：比较普通 VACUUM 与 VACUUM FULL 的磁盘及锁行为；使用独立测试库。
- v4：观察 autovacuum 触发与滞后；报告统计的近似性和观测窗口。

边界：本模块针对固定 PostgreSQL 版本，不能将行为直接推广到所有 MVCC 数据库。

## 5. 领域二：Transactions and Isolation

### T01. 事务边界与隔离异常

覆盖：ACID Properties、Dirty Read、Read Skew、Phantom Read。
目标：`labs/transactions/isolation/`。前置：基本 SQL。
场景：账户转账与余额报表。模型：账户、事务、SQL 语句、并发执行轨迹。
不变量：已提交转账保持总余额；实验明确每条读取发生在哪个事务和快照中。

- v0：事务内转账与故意失败回滚；核对两个账户的余额和总和。
- v1：协调两个连接读未提交更新；证明 PostgreSQL 不允许脏读，包括其 READ UNCOMMITTED 行为。
- v2：在 READ COMMITTED 下用两条 SELECT 构造 Read Skew；记录中间提交位置。
- v3：重复范围查询并插入匹配行；比较 READ COMMITTED 与 REPEATABLE READ 的可见结果。
- v4：汇总隔离实验轨迹，分开解释 ACID 四个属性；不将业务规则自动归功于数据库。

边界：不能为了展示每种异常而声称 PostgreSQL 支持它；必要的允许脏读模型应单独标为模拟。

### T02. MVCC 与 Snapshot Isolation

覆盖：MVCC (Multi-Version Concurrency Control)、Snapshot Isolation、Write Skew。
目标：`labs/transactions/mvcc/`。前置：T01。
场景：两个值班医生分别申请下班。模型：行版本、快照、事务、提交顺序。
不变量：每次读取符合所声明的快照规则；“至少一人值班”作为可被反例击破的业务约束。

- v0：用真实数据库的两个事务展示旧快照仍可读取旧值；记录开始与快照建立的区别。
- v1：建立最小版本可见性模型，并与数据库轨迹对照；不复制 PostgreSQL 全部实现。
- v2：在 PostgreSQL REPEATABLE READ 下确定性复现 Write Skew；两个事务写不同行仍破坏约束。
- v3：增加跨行约束保护策略并对比；解释快照隔离为何不等于可串行化。

边界：修复方案应明确冲突点与重试责任；Vacuum 的实际回收另见 S07。

### T03. 乐观锁、悲观锁与死锁

覆盖：Optimistic Locking、Pessimistic Locking、Deadlock、Lock Escalation。
目标：`labs/transactions/locking/`。前置：T01、T02。
场景：多人扣减同一商品库存。模型：库存、版本号、锁拥有者、等待关系。
不变量：库存不因并发丢失更新，也不能减为负数。

- v0：协调两个读取后覆盖写入，复现丢失更新。
- v1：使用版本条件更新；验证一个竞争者成功，另一个明确获知冲突。
- v2：使用行锁保护读取与更新；比较冲突率、等待时间和持锁时长。
- v3：反向顺序锁定两行制造死锁；验证数据库中止一方，按固定顺序加锁后避免该模式。
- v4：用独立锁管理模拟展示锁升级的内存收益和阻塞扩大；明确 PostgreSQL 不做 SQL Server 式行锁升级。

边界：模拟锁升级与数据库实测必须分开；不引入额外商业数据库作为默认依赖。

### T04. Serializability 与事务重试

覆盖：Serializability。目标：`labs/transactions/serializable/`。前置：T02、T03。
场景：保护值班约束或预约容量。模型：事务历史、读写冲突、提交与中止。
不变量：已提交结果能对应某个串行执行顺序；可串行化本身不自动保证所有业务约束。

- v0：枚举小规模串行结果，作为并发实验的参考集合。
- v1：以数据库 SERIALIZABLE 运行 Write Skew 场景；验证某个事务被中止。
- v2：针对序列化失败重试整个事务；验证重新读取并重新判断业务条件。
- v3：施加竞争负载；报告吞吐、失败和重试次数，区分 serializability 与 strict serializability。

## 6. 领域三：Partitioning and Scaling

### P01. 哈希、范围与一致性哈希

覆盖：Database Sharding、Hash Partitioning、Range Partitioning、Consistent Hashing。
目标：`labs/partitioning/routing/`。前置：哈希、基本数据服务。
场景：按租户保存订单。模型：键、分片、路由表、节点集合。
不变量：在同一路由版本下，写入和读取必须定位到相同分片。

- v0：单分片保存订单；建立点查和范围查询基准。
- v1：采用 hash(key) mod N；验证分布并测量从 N 到 N+1 的键移动比例。
- v2：采用范围分区；检查边界、范围扫描和递增键集中写入。
- v3：采用一致性哈希与虚拟节点；比较迁移比例和负载分布，不宣称它消除热点。

### P02. 数据倾斜、热点与水平扩展

覆盖：Data Skew、Hot Partition、Horizontal Scaling。
目标：`labs/partitioning/skew/`。前置：P01、F02 的负载测量知识。
场景：一个大客户产生大部分请求。模型：键频率、分片容量、队列、请求延迟。
不变量：负载统计能按分片归因，不能只看集群平均值。

- v0：生成均匀和倾斜分布，记录各分片的数据量与请求量。
- v1：固定单个热键并增加节点；证明新增节点可能无法分担该键。
- v2：对可拆分的聚合写入增加子键；验证汇总正确并量化额外读取成本。
- v3：比较扩容前后的尾延迟和饱和点；说明水平扩展受热点及共享瓶颈限制。

### P03. Resharding 与 Rebalancing

覆盖：Resharding、Rebalancing。目标：`labs/partitioning/migration/`。前置：P01、D01。
场景：服务在线时把数据迁移到新分片。模型：路由版本、复制进度、写入序列、切换状态。
不变量：已确认写入不能因路由切换丢失；过期路由请求必须被拒绝或正确处理。

- v0：暂停写入后迁移数据；校验源目标行数和内容摘要。
- v1：后台复制历史数据；展示复制期间新增写入造成的缺口。
- v2：记录并重放迁移期间的增量；验证更新、删除和重复投递。
- v3：设置短暂写入屏障，追平后切换路由版本；验证过期客户端与边界请求。
- v4：在复制、追平、切换阶段中断并恢复；比较改变分片划分和仅移动现有分片的区别。

边界：首个完成版本允许短暂停写，不宣称零停机迁移；不把双写本身当作一致性协议。

## 7. 领域四：Replication and Read Consistency

### R01. 主从复制与读取副本

覆盖：Leader–Follower Replication、Read Replicas。
目标：`labs/replication/leader_follower/`。前置：S03、T01。
场景：订单写主节点，查询走副本。模型：主节点、日志位置、副本应用位置、确认策略。
不变量：同一副本按规定顺序应用已接受的日志；读到的数据对应明确应用进度。

- v0：两个进程按日志复制键值更新；验证顺序和重启后的进度。
- v1：人为延迟副本应用；稳定复现写入后立即读副本看不到更新。
- v2：返回写入位置作为读取门槛；验证等待、超时与读主策略。
- v3：比较异步确认与等待副本确认；记录延迟和故障下的数据保留情况。
- v4：中断复制再追平；验证重复接收和断点恢复。

边界：此教学协议不提供自动选主；确认日志接收、持久化和应用是三种不同条件。

### R02. 一致性模型与读取契约

覆盖：Eventual Consistency、Strong Consistency、Consistent Reads、Read Repair。
目标：`labs/replication/consistency/`。前置：R01。
场景：用户修改资料后刷新页面。模型：版本、客户端会话、读取历史、修复条件。
不变量：各实验满足自己声明的读取契约；“strong”必须细化为可检验的定义。

- v0：异步复制暴露旧读，观察停止写入后的收敛条件。
- v1：增加会话写入版本，提供 read-your-writes；展示其他客户端仍可能读旧值。
- v2：在固定主节点且无故障切换的模型中定义线性一致读写；记录历史并核对实时先后关系。
- v3：对明确单写者、有序版本的模型实施 Read Repair；证明被读取副本得到修复。
- v4：比较会话一致、快照一致、最终一致与线性一致；加入分区反例说明各自边界。

边界：Read Repair 不自动修复从未读取的键；持续收敛需说明后台修复等额外条件。
小规模历史检查只能证明测试历史，不能形式化证明整个实现。

### R03. 多主与地理复制

覆盖：Multi-Leader Replication、Geo-Replication。
目标：`labs/replication/multi_leader/`。前置：R01、R02、C01。
场景：两个地区都要低延迟写入。模型：地区节点、版本元数据、冲突、合并规则。
不变量：节点收敛规则明确，且不能把冲突丢失静默描述成无损同步。

- v0：单主跨地区延迟模拟，测量远端写入成本。
- v1：允许双主写入并制造分区；复现同键并发冲突。
- v2：采用确定性的 last-write-wins 规则；展示时钟偏移与更新丢失代价。
- v3：对可合并计数器使用明确合并规则；验证重复、乱序传播后的收敛。
- v4：对比单主、多主在分区下的可用性、冲突与延迟，不把多地区等同于多主。

### R04. 物理复制与逻辑复制

覆盖：Physical Replication、Logical Replication。
目标：`labs/replication/postgres/`。前置：R01，固定版本 PostgreSQL。
场景：建立备库与选择性同步业务表。模型：WAL 位置、复制槽、发布、订阅。
不变量：复制进度可观测；积压与磁盘增长必须能关联。

- v0：配置物理流复制，核对数据和只读行为。
- v1：配置逻辑发布订阅，验证选定表的增删改传播。
- v2：比较 DDL、序列和复制标识的实际限制；以固定版本文档和实验为准。
- v3：暂停消费者造成积压再恢复；观察复制槽保留 WAL 的磁盘代价。

## 8. 领域五：Consensus and Network Partitions

### C01. CAP、Quorum 与不可区分的故障

覆盖：CAP Theorem、Quorum、Two Generals Problem。
目标：`labs/consensus/partitions/`。前置：R02。
场景：两个机房失联，无法区分对端宕机还是消息延迟。模型：节点、消息、历史、分区。
不变量：安全性和活性分别陈述；超时不能被当作对方一定死亡的证明。

- v0：控制消息延迟和丢弃，展示超时后无法确认远端操作是否完成。
- v1：用确认消息丢失轨迹解释 Two Generals Problem；不把它混同于 Raft 的故障模型。
- v2：在网络分区时分别选择拒绝请求和允许旧读；明确 CAP 的线性一致性与可用性定义。
- v3：实验读写 Quorum 的集合交集；构造反例说明 R+W>N 本身不足以保证线性一致性。

### C02. 选主、租约与 Split-Brain

覆盖：Leader Election、Split-Brain。
目标：`labs/consensus/election/`。前置：C01；fencing 实验参照 D02。
场景：后台调度器需要唯一有效写入者。模型：候选人、任期、租约、被保护资源。
不变量：资源只接受有效领导任期的写入，旧领导恢复后不能继续破坏状态。

- v0：用心跳超时自选主，复现分区导致双主。
- v1：在模拟器中加入任期和多数投票；检查同一任期最多一个获多数票的领导者。
- v2：持久化任期与投票记录；节点重启后不得在同一任期重复投票。
- v3：演示租约过期与旧领导长暂停；由资源端校验 fencing token，拒绝旧写入。
- v4：对比分区、长 GC 暂停和重启；区分“认为自己是主”和“被允许修改资源”。

边界：选主模块不意味着已实现复制日志共识；不保证全局永远只有一个进程自认为领导者。

### C03. Raft 的日志共识

覆盖：Raft Consensus Algorithm。目标：`labs/consensus/raft/`。前置：C01、C02、S03。
场景：三个节点维护同一份配置状态。模型：任期、日志、提交位置、状态机、持久状态。
不变量：已提交日志不能被未来领导者覆盖；节点以相同顺序应用相同已提交命令。

- v0：单节点日志驱动确定性状态机；建立命令执行参考模型。
- v1：接入持久任期、投票和选举计时；重放同时竞选与节点重启轨迹。
- v2：加入 AppendEntries 和前缀检查；验证冲突日志被修复。
- v3：实现多数复制与提交推进，明确当前任期提交规则；构造旧任期日志的反例。
- v4：限制候选人的日志新旧条件；验证落后节点不能取代含已提交记录的合法领导者。
- v5：在各持久化边界崩溃并重启；验证恢复后提交与应用结果。
- v6：注入丢包、重复、乱序和分区；核对提交历史以及多数恢复后的进展。
- v7：加入快照和日志压缩；验证落后节点通过安装快照追平。
- v8：回放完整故障集并接入真实多进程演示；生产演示优先使用成熟共识服务，对比教学模型边界。

边界：动态成员变更、联合共识和线性一致读协议另设进阶扩展；当前版本不宣称具备这些能力。
这是高复杂度模块，v2–v7 可各展开多篇；模拟测试不能替代算法证明或生产验证。

## 9. 领域六：Distributed Coordination and Transactions

### D01. 幂等与 Exactly-Once 的边界

覆盖：Idempotency、Exactly-Once Semantics。
目标：`labs/coordination/idempotency/`。前置：T03、F03。
场景：创建订单成功但响应丢失，客户端重试。模型：请求键、请求摘要、业务记录、响应记录。
不变量：同一请求键和载荷只产生一次约定范围内的业务效果；不同载荷复用键必须拒绝。

- v0：提交后丢弃响应，复现重复订单。
- v1：引入请求键和唯一约束；验证串行及并发重复请求。
- v2：把业务变更与去重结果放进同一事务；在事务各边界中断并重试。
- v3：增加请求摘要与结果重放；验证键冲突、处理中状态和结果保留期限。
- v4：增加外部邮件效果，展示本地事务无法自动去重外部副作用；用支持幂等键的接收端验证范围内的单次效果。

边界：Exactly-Once 必须说明作用域、持久化条件和去重期限，不能宣称网络只投递一次。
接收端不支持幂等时，应明确残余重复风险。

### D02. 分布式锁与 Fencing

覆盖：Distributed Locking。目标：`labs/coordination/locks/`。前置：D01、C01。
场景：多个 worker 更新同一份导出文件。模型：锁拥有者、租约、单调令牌、资源版本。
不变量：过期拥有者的写入在被保护资源处遭拒。

- v0：用原子条件获取锁，验证并发竞争只有一方成功。
- v1：加入租约过期；复现长暂停导致旧拥有者和新拥有者同时工作。
- v2：为新拥有者分配单调 fencing token；验证资源端拒绝旧 token。
- v3：实现拥有者校验的续租与释放；防止旧拥有者释放新拥有者的锁。
- v4：中断锁服务或资源服务；记录安全性、可用性和不确定结果的处理。

边界：锁服务提供唯一令牌不代表资源自动受保护；生产选型需成熟协调服务。

### D03. 分布式事务、2PC 与 3PC

覆盖：Distributed Transactions、Two-Phase Commit (2PC)、Three-Phase Commit (3PC)。
目标：`labs/coordination/commit/`。前置：T04、C01、S03。
场景：两个独立资源共同提交一次转账。模型：协调者、参与者、持久决定、准备状态。
不变量：同一事务不能在一个参与者提交、另一个参与者最终回滚。

- v0：依次提交两个数据库，故意让第二个失败，复现不一致。
- v1：用 PostgreSQL prepared transactions 实验 2PC 正常路径；核对资源配置与清理流程。
- v2：协调者在 prepare 后崩溃；观察锁与 in-doubt 状态，并按持久决定恢复。
- v3：用显式状态机模拟 3PC 的 pre-commit 阶段；比较与 2PC 的状态及通信成本。
- v4：违反 3PC 所需的时序和故障假设；展示它不普遍解决异步网络分区问题。

边界：3PC 主要作为模型实验；不能把超时后自行决定当作通用安全实现。

### D04. Saga 与补偿

覆盖：Saga Pattern。目标：`labs/coordination/saga/`。前置：D01、D03 的原子性边界。
场景：订单依次预留库存、扣款、安排配送。模型：步骤、持久状态、业务效果、补偿操作。
不变量：每一步及其补偿可去重；失败流程最终进入可解释的完成、已补偿或待人工处理状态。

- v0：串行调用三个服务，展示中途失败留下的部分效果。
- v1：持久化步骤进度并在重启后续跑；验证不会盲目重新执行已完成步骤。
- v2：定义逆序补偿；验证退款与库存释放，不把补偿描述成数据库回滚。
- v3：让补偿本身超时或失败；验证重试、去重和人工处理状态。
- v4：模拟并发订单观察中间状态；说明 Saga 的隔离限制及业务保护措施。

## 10. 领域七：Data Modeling and Query Performance

### Q01. 规范化与反规范化

覆盖：Normalization、Denormalization。
目标：`labs/query/modeling/`。前置：T01。
场景：订单中保存商品当前名称与购买时价格。模型：实体、关系、函数依赖、历史快照字段。
不变量：业务历史不会因商品当前信息更新而被意外改写。

- v0：单表重复保存客户资料，复现更新不一致。
- v1：按明确函数依赖拆表并建立约束；验证更新和连接查询。
- v2：为具体读取增加冗余字段；记录维护责任和一致性要求。
- v3：区分冗余副本与必要的历史快照；比较读成本、写成本和异常风险。

### Q02. 二级索引与覆盖读取

覆盖：Secondary Index、Index-Only Scan。
目标：`labs/query/indexes/`。前置：Q01；S02 提供内部机制补充。
场景：按用户与时间查询最近订单。模型：表、索引键、回表、可见性信息。
不变量：优化前后返回相同结果，不以一次耗时作为全部证据。

- v0：对无索引查询记录 EXPLAIN 与实际读取量。
- v1：建立二级索引；验证选择性高低时执行方式的变化。
- v2：设计复合索引并比较列顺序；测试过滤、排序与范围条件。
- v3：构造 Index-Only Scan，再更新表观察 heap fetches；解释 PostgreSQL 可见性映射与 Vacuum 的影响。

### Q03. Query Planner 与成本估计

覆盖：Query Planner、Cost-Based Query Optimization。
目标：`labs/query/planner/`。前置：Q02、P02 的倾斜概念。
场景：同一 SQL 在数据增长后突然变慢。模型：统计信息、估算行数、候选路径、实际执行。
不变量：估算与实测分开报告，诊断依据来自执行计划和数据分布。

- v0：比较顺序扫描与索引扫描的适用数据规模。
- v1：制造失真的统计信息，再 ANALYZE；检查估算误差和计划变化。
- v2：引入相关字段与倾斜；观察独立性假设失效，并测试适当统计信息。
- v3：比较连接策略和排序溢出；报告 CPU、I/O、内存与执行时间的关联。

### Q04. 物化视图与缓存

覆盖：Materialized Views、Caching。
目标：`labs/query/derived/`。前置：Q01、D01；并发失效实验需 T03。
场景：仪表盘反复计算每日销售额。模型：源数据、派生结果、刷新位置、过期策略。
不变量：每种读取方式标明可接受的新鲜度；过期结果不能冒充实时数据。

- v0：每次查询现场聚合，建立正确性基准和成本。
- v1：使用物化视图，展示写入后尚未刷新的结果。
- v2：比较刷新方式及读取阻塞；检查数据库对并发刷新的前提。
- v3：实现简单 cache-aside，控制 TTL；验证未命中和过期。
- v4：构造写入与缓存填充竞态；采用明确版本或失效策略，并测量残余旧读窗口。

## 11. 领域八：Traffic and Resource Management

### F01. 连接池、复用与连接泄漏

覆盖：Connection Pooling、Connection Multiplexing、Database Connection Leaks。
目标：`labs/traffic/connections/`。前置：T01、基础 HTTP/数据库客户端。
场景：并发 API 把数据库连接耗尽。模型：请求、客户端连接、后端连接、等待者。
不变量：请求结束后释放所占资源；连接和等待队列均有明确上限。

- v0：每次请求建立连接，测量握手与连接数量。
- v1：引入有界连接池；验证复用、等待和获取超时。
- v2：故意漏还连接，观察池耗尽；用上下文管理与异常路径检查修复。
- v3：用事务池代理实验多个客户端复用后端连接；验证会话状态限制，说明 pooling 不等于任意协议并发 multiplexing。

### F02. 负载均衡、限流与背压

覆盖：Load Balancing、Rate Limiting、Backpressure。
目标：`labs/traffic/admission/`。前置：F01。
场景：请求到达速度持续超过 worker 处理速度。模型：到达率、队列、容量、拒绝响应。
不变量：系统内在途工作有界；不能以无限排队伪装成功接收。

- v0：无界排队，记录队列增长、内存与等待时延。
- v1：使用有界队列，让生产者等待或收到拒绝；验证内存与在途工作上限。
- v2：增加明确速率和突发容量的令牌桶；验证边界与公平性限制。
- v3：将请求分配到多个 worker；比较轮询与在途请求感知策略。
- v4：降低一个 worker 的处理能力；观察尾延迟并验证端到端背压传播。

### F03. Retry Storm 与 Circuit Breaker

覆盖：Retry Storm、Circuit Breaker。
目标：`labs/traffic/resilience/`。前置：F02；副作用请求在 D01 后重做。
场景：依赖短暂失败导致所有客户端立即重试。模型：尝试次数、截止时间、重试预算、断路状态。
不变量：请求总尝试数和总耗时有界；不可重试错误不得进入重试循环。

- v0：立即重试，记录放大后的下游请求量。
- v1：区分可重试故障与永久错误，并设置总截止时间。
- v2：加入指数退避与 jitter；固定随机种子比较重试时间分布。
- v3：实现 closed/open/half-open 转换；验证探测数量有界及恢复行为。
- v4：组合多层调用，验证重试预算限制乘法放大；说明断路器不替代限流与背压。

### F04. Thundering Herd 与请求合并

覆盖：Thundering Herd Problem。
目标：`labs/traffic/herd/`。前置：F03、Q04。
场景：热门缓存键同时过期，大量请求回源。模型：缓存键、填充者、等待者、过期时间。
不变量：合并等待者的取消或超时不得破坏其他请求；回源失败不能无限等待。

- v0：同步过期重现回源尖峰，并统计峰值并发。
- v1：在单进程内合并同键请求；验证只有一次回源及正确结果传播。
- v2：测试填充者失败、取消与超时；验证等待者得到确定结果。
- v3：比较随机化过期与 stale-while-revalidate；明确单进程合并无法消除跨节点重复。

## 12. 领域九：Availability and Recovery

### A01. 备份与 Point-in-Time Recovery

覆盖：Backups vs. Point-in-Time Recovery。
目标：`labs/recovery/backup/`。前置：S03、R04。
场景：误删订单后恢复到删除前。模型：基础备份、WAL 归档、恢复目标、恢复实例。
不变量：恢复结果必须经业务数据核对；文件存在不等于备份可用。

- v0：做逻辑备份并恢复到独立数据库；核对表、行数与约束。
- v1：在备份后写入新订单；展示单次备份无法恢复后续数据。
- v2：配置物理基础备份和 WAL 归档；检查归档连续性。
- v3：执行误删并恢复到删除前的明确恢复点；验证后续误操作不在恢复结果中。
- v4：删除一段归档或损坏备份副本，验证恢复失败能被识别；测量恢复时间和数据损失窗口。

边界：所有破坏实验仅针对临时实例；副本会复制误删，因此不能替代备份。

### A02. Checkpoint 与有界恢复

覆盖：Checkpointing。
目标：`labs/recovery/checkpoint/`。前置：S03；本模块扩展其日志存储检查点。
场景：日志越来越长，服务重启越来越慢。模型：状态快照、日志位置、发布元数据、保留范围。
不变量：快照状态与日志位置匹配；恢复所需的日志不得提前删除。

- v0：仅重放完整日志，测量恢复工作量随日志长度增长。
- v1：在暂停写入条件下生成快照并记录位置；验证快照加尾部日志得到相同状态。
- v2：原子发布快照元数据后再回收日志；在发布前后注入崩溃。
- v3：损坏最新快照并尝试保留的上一检查点；明确备用快照所需日志仍须保留。

边界：首次实现允许暂停写入；不停写快照是后续扩展，不将应用检查点与数据库 checkpoint 完全等同。

### A03. High Availability 与 Failover

覆盖：High Availability (HA)、Failover。
目标：`labs/recovery/ha/`。前置：R02、C02、A01。
场景：主库进程或网络故障后恢复服务。模型：健康状态、主角色、客户端路由、数据恢复目标。
不变量：故障切换不能留下可写旧主；数据丢失范围必须与复制策略一致。

- v0：定义 RTO、RPO 和测量窗口；记录单实例故障下的服务中断。
- v1：手动提升副本并切换客户端；核对已确认写入的保留情况。
- v2：用成熟 HA 组件自动检测与切换；记录误判条件和旧主隔离措施。
- v3：只隔离网络、不杀死旧主；验证 fencing 与重连行为。
- v4：旧主重新加入并演练回切；报告实际 RTO/RPO 和客户端重试影响。

边界：不从一次成功演练推断年度可用性，不将多数节点在线视为整个业务一定可用。

## 13. 领域十：Data Movement and Application Architecture

### E01. CDC 与投影同步

覆盖：Change Data Capture (CDC)。
目标：`labs/dataflows/cdc/`。前置：R04、D01。
场景：订单更新需要同步到检索或报表存储。模型：源记录、变更事件、消费位置、目标投影。
不变量：快照与增量之间无遗漏；重复事件不造成重复业务效果。

- v0：应用分别写两个存储，第二次写失败时复现不一致。
- v1：从数据库变更流读取已提交增删改；记录事件键、版本和来源位置。
- v2：建立初始快照与增量衔接；按所选连接器的具体协议检查切换窗口。
- v3：目标更新与消费进度协调持久化；在提交边界崩溃，验证重放和去重。
- v4：暂停消费者并恢复；观测复制滞后、积压和源端 WAL 保留。

边界：传输不默认有全局顺序；需明确表、分区与事务范围，跨模块沿用已冻结连接器版本。

### E02. Schema Evolution

覆盖：Schema Evolution。
目标：`labs/dataflows/schema/`。前置：E01、Q01。
场景：线上给订单增加必填字段，同时旧客户端仍在运行。模型：生产者、消费者、schema 版本、回填状态。
不变量：发布顺序中的每个中间状态都满足明确兼容矩阵。

- v0：直接增加必填字段，复现旧客户端写入失败。
- v1：先增加兼容字段和默认读取语义；验证新旧客户端组合。
- v2：分批回填并切换读写；验证重复执行、部分失败与进度恢复。
- v3：确认旧客户端退出后收紧约束并删除过渡逻辑；验证最终 schema 与清理完成。

边界：这里的过渡逻辑是实验学习对象，最终检查点必须移除；事件 schema 与表 schema 分别验证。

### E03. Event Sourcing 与反规范化读模型

覆盖：Event Sourcing、Denormalized Read Models。
目标：`labs/dataflows/events/`。前置：D01、Q04、E02。
场景：需要追溯订单状态如何变化并重建查询视图。模型：命令、事件流、流版本、投影位置。
不变量：同一事件序列产生同一领域状态；投影重建不能再次发送邮件或扣款。

- v0：当前状态表只能说明结果，展示无法解释历史变化的限制。
- v1：追加领域事件并重放状态；验证事件顺序和非法状态转换。
- v2：以预期流版本控制并发追加；验证冲突不会静默覆盖。
- v3：构建反规范化读模型；验证重复消费、滞后和从头重建。
- v4：引入事件版本变化并重放旧数据；将状态重建与外部副作用隔离。

边界：Event Sourcing 不等于 CDC；前者把领域事件作为事实来源，后者捕获已有存储的变更。

### E04. Data Warehouse 与 Federation

覆盖：Data Warehouse、Federation。
目标：`labs/dataflows/analytics/`。前置：S06、E01、E02、Q03。
场景：联合订单库与客户数据生成销售分析。模型：数据源、摄取批次、分析模型、查询计划。
不变量：报表说明数据截止时间与来源；重跑同一批次不会重复计数。

- v0：把两个来源导入小型分析库，建立可核对的批次与聚合结果。
- v1：实现增量装载并处理迟到更新；验证去重与历史修正策略。
- v2：通过固定版本的联邦查询能力直接访问两个源；观察谓词下推与远程扫描量。
- v3：对比复制到仓库与实时联邦查询；注入源不可用和两源不同步，报告成本、新鲜度与一致性边界。

边界：可用 DuckDB 作为小规模分析实验环境，不宣称实现完整企业数仓；联邦查询不自动提供跨源一致快照。

## 15. 统一实验与教程验收规范

### 每个版本细化时必须写清楚

2. 真实调用者、输入输出、限制条件，以及最小模型为何仍保留问题本质。

5. 精确文件与调用者修改；局部补丁后提供完整当前检查点，不能要求读者拼接隐含代码。
6. 正常、错误输入、故障、边界与并发轨迹的检查方法及预期结果。
7. 完成后的能力、已知限制、下一版需要解决的问题。

预热方式和重复次数；比较趋势与机制，不许写脱离环境的固定性能承诺。

## 16. 第一个可直接展开的教程：T01 v0

为避免直接从抽象术语开始，建议先写“转账中途失败，如何保持两个账户的余额正确”。
总路线覆盖全部模块；本节才是按 `from-scratch-tutorial-plan` 细化的单版本写作计划。
其余版本进入写作前也必须完成同等细化，不能拿一句里程碑直接当教程正文。

### 读者、场景与压缩模型

读者会写 Python 函数和简单 SQL。读者完成后能通过同一个入口运行成功转账、
故意失败转账和无效金额请求，并用数据库查询验证结果。

场景：账户 A 向 B 转账，第一次扣款后程序失败。压缩模型只保留两个账户、整数金额、
两条 UPDATE 和一个故障点；暂不讨论并发、分布式事务、外部支付和货币精度转换。
即使只有两个账户，仍保留“多步修改必须共同成功或共同失败”的核心压力。

核心概念：账户余额、转账请求、事务边界、提交/回滚。初始 A=100、B=100，转账 30。
不变量：成功后 A=70、B=130；失败后仍为 100/100；任何完成结果中余额总和为 200。

外部契约：请求给出来源 ID、目标 ID、正整数金额；来源目标存在且不同，余额充足。
金额和 ID 在调用入口验证；扣减处用条件 UPDATE 保护余额。
正常返回成功，故障返回明确失败；错误不能被吞掉后报告成功。
数据库连接信息来自环境，不写入文档或 Git。故障开关仅存在于实验入口。

依赖图：成功的两条更新 → 扣款后故障 → 观察部分提交 → 添加事务边界 → 重新验证 → 冻结完整检查点。

### 任务 1：建立可运行的实验输入

描述：编写环境准备与两账户初始化教程，从一次普通转账开始。
文档目标：`tutorials/02-transactions-isolation/01-isolation/v0/tutorial.md` 的环境与起点。
代码目标：`labs/transactions/isolation/schema.sql`、`transfer.py` 及根 Python 依赖声明。
代码角色：checkpoint；提供当前完整初始化脚本和入口。前置：无。规模：S。

验收：固定 PostgreSQL 与驱动版本，uv 安装后可连接临时数据库；用参数化 SQL 完成两条更新。
基线故意使用每条语句独立提交，必须明确写出该设置，避免驱动默认事务掩盖问题。
验证：重置测试数据后转账 30，检查 A=70、B=130；环境命令仍需在编写时实际验证。
检查点提交：否，本任务尚未形成完整教学闭环。

### 任务 2：用扣款后的故障暴露部分提交

描述：在两条 UPDATE 之间引入确定性的实验异常，让读者先看到错误余额。
前一基线：两条语句独立提交。压力：A 已扣 30 后、B 尚未收到钱时入口失败。
断点：返回失败但数据库为 A=70、B=100，总额减少。
新要求：这两次修改必须共同提交。此任务只新增故障触发，不提前加入事务修复。
文档目标：同一教程的问题复现段。代码目标：`transfer.py`。代码角色：patch。
前置：任务 1。规模：S。检查点提交：否。

验收与验证：每次重置后都能得到 70/100，无随机等待；保留 SQL 执行和异常发生顺序。
冻结：错误已可重现，下一任务解决共同提交。

### 任务 3：用事务边界恢复原子性

描述：把两条 UPDATE 放入明确事务，异常离开事务时回滚。
前一基线：任务 2 的可复现部分提交。压力：同样的故障触发必须不再留下扣款。
改变：只替换提交边界，不新增重试、锁服务或通用事务封装。
文档目标：同一教程的修复与检查段。代码目标：`transfer.py`。
代码角色：patch。前置：任务 2。规模：M。检查点提交：否。

验收：事务成功退出才提交；异常路径回滚并向调用者返回失败；入口金额验证保持原位。
验证：成功为 70/130，扣款后失败为 100/100；零金额、负金额、余额不足不修改数据。
冻结：单数据库内的两步修改具备本实验验证的原子性；尚未研究并发可见性。

### 任务 4：组装、重放并冻结 v0

描述：呈现完整当前脚本、初始化 SQL、检查代码及运行命令；不增加之前未解释的逻辑。
文档目标：同一教程的完整检查点、预期输出与下一步。
代码目标：完整 `labs/transactions/isolation/` 及 `tests/transactions/isolation/`。
代码角色：checkpoint。前置：任务 3。规模：M。

验收：从干净数据库执行教程全部命令，成功和失败案例均可重复；异常连接正确释放。

### Helper 边界与审查风险

只在测试开始需要重复初始化时提供测试 fixture：调用者为测试，用临时数据库连接初始化两行，
输出测试连接或数据库标识，影响范围仅实验表。运行入口直接使用数据库驱动事务 API，
不引入 repository、unit-of-work 或事务装饰器。

审查时优先检查：驱动默认 autocommit 是否导致基线失真；错误是否被捕获后误提交；
测试是否读取了真正提交后的数据库状态；是否误把单事务原子性说成完整 ACID 已得到验证。

写作交接：使用 `from-scratch-tutorial-build`，按任务 1 → 2 → 3 → 4 执行。

在提交说明中记录压力、基线、修复、验证、冻结能力与下一缺口；代码提交另外按实际范围处理。

## 17. 分阶段执行与工作量

以下是安排顺序的建议，不是完成期限承诺。模块有前置时，以模块前置为准。

1. 建立实验习惯：完成 T01 v0，冻结一篇可以从空环境重放的示范教程。
2. 数据库与服务基础：T01–T04、Q01–Q03、F01–F03；形成并发、连接与流量的直觉。
3. 存储内部机制：S01–S07；结合真实数据库观察与教学存储实现，尤其保留崩溃边界。
4. 扩展和复制：P01–P02、R01–R04、C01；先理解数据如何分布、为何会读旧。
5. 协调和恢复：D01–D04、P03、C02、A01–A03；形成可重试、可恢复的执行链。
6. 深入与数据架构：C03、Q04、F04、E01–E04；完成共识、派生数据与异步演进实验。

F03 首轮只用无副作用请求；完成 D01 后再补齐副作用重试实验。
C02/D02 可先分别运行其最小前置版本，再交叉完成 fencing 实验，避免误解为循环依赖。

粗略投入仅用于判断规模：一个普通版本的实现、实验和初稿可能需要 4–12 小时；
存储恢复、在线迁移、Raft 等复杂版本可能需要 12–30 小时以上。环境排错、正式写作和复核另计。
这是长期学习项目，不能把约两百个能力检查点理解为几十篇速成文章。

先用前 3 个实际版本记录耗时，再校正范围与节奏。对已掌握模块可以运行验收实验后跳过正文，
但不能跳过被后续模块引用的格式、契约与已知限制。
