# S03 v3-v4 and T02 v1-v3 independent review

## Findings and fixes

T02 v2/v3 initially required revision: instructions said to replace only the
previous transaction block, leaving contradictory final assertions from the
preceding experiment. v2 could retain count==1 after demonstrating count==0;
v3 could retain count==0 after protecting one doctor. Reviewer requested an
explicit replacement region including previous assertions, plus an exact
guard.sql initialization call.

Author amended both replacement instructions and supplied the SQL call.
Reviewer independently reconstructed the T01 runner, applied the revised
whole-region patches, and ran serial, skew, conflict, and retry experiments.
All passed against the real isolated PostgreSQL database.

No remaining required fixes found in these versions.

## Verdicts

- S03 v3: pass. Committed groups, abandoned operations, transaction-ID reuse,
  tail repair, derived data, and validation before mutation have explicit
  contracts. The guide separates atomic recovery from business invariants.
- S03 v4: pass. The declared POSIX/preexisting-directory fault model matches
  file and directory synchronization. Failure before acknowledgement is
  tested, and a readable complete commit after fsync failure is correctly
  presented as an uncertain outcome, not an abort.
- T02 v1: pass. The committed-version teaching model is explicitly limited
  and is not passed off as PostgreSQL's full visibility algorithm.
- T02 v2: pass after instruction revision. Real RR transactions preserve
  individual snapshots yet leave both doctors off call; final rows are checked.
- T02 v3: pass after instruction revision. Guard UPDATE creates a real RR
  stale-snapshot write conflict; retry occurs in a new transaction and reruns
  the business predicate. All cooperating writers must follow the protocol.
