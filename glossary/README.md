## 存储引擎

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| B-Tree | 保持有序、平衡且每个节点包含多个键的搜索树。数据库常用其 B+Tree 变体，把记录或记录指针放在叶子，支持订单号点查和时间区间扫描。 | 分裂和合并带来写入工作；并发控制与崩溃恢复不是树结构自动提供的。 | S02 |
| LSM Tree | 先把更新写入内存结构，再刷成不可变有序文件，通过后台合并管理多个版本。适合持续追加、更新的键值负载。 | 查询可能检查多个文件；合并产生额外读写和短时空间占用。 | S05 |
| Write-Ahead Logging (WAL) | 在数据页修改被持久化之前，先持久化恢复该修改所需的日志。进程崩溃后可按协议恢复已提交更新。 | 只有调用 write 并不等于日志耐断电；确认、flush、fsync 和提交记录顺序必须明确。 | S03 |
| Bloom Filter | 紧凑的概率成员过滤器：回答“不存在”或“可能存在”。查询不存在的键时，可避免读取某些 SSTable。 | 有假阳性，正确维护时无假阴性；普通版本不能直接删除元素。“可能存在”还需查真实数据。 | S04 |
| Columnar Storage | 把同一列的值相邻存储。统计订单金额时不必读取每行的大段备注，还便于编码与压缩。 | 点查整行、频繁小更新可能更昂贵；列存不自动等于向量化执行。 | S06 |
| Data Locality | 将经常一起访问的数据放在接近的内存或存储位置。顺序读取相邻订单通常比跨许多页随机访问更容易利用缓存。 | 布局有利于一种访问模式，可能不利于另一种；CPU 缓存、OS 页缓存和磁盘访问是不同层次。 | S01 |
| Compaction | 在 LSM 等系统中合并存储文件，按版本规则消除冗余值并在安全时清除删除标记。 | 合并消耗带宽且需要临时空间；过早丢弃 tombstone 会使旧值重新出现。 | S05 |
| Write Amplification | 实际写入存储的字节数与逻辑业务写入字节数之比。例如更新 1 MB 触发多轮文件合并。 | 必须标明测量层次；WAL、文件系统和设备内部可能各有放大，不能混用分子。 | S05 |
| Database Vacuuming | 在 PostgreSQL 中回收不再被快照需要的旧元组空间，并维护相关信息。更新很多次但行数不变的表仍需要它。 | 长事务可能阻碍回收；普通 VACUUM 通常让空间可复用，并不保证文件马上缩小。 | S07 |

## 事务与隔离

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| ACID Properties | 原子性、约束意义上的一致性、隔离性、持久性。转账必须共同完成、遵守约束，并按明确隔离与持久化契约执行。 | 数据库不会自动推导“至少一个医生值班”等业务规则；证明回滚只证明其中一部分。 | T01 |
| MVCC (Multi-Version Concurrency Control) | 保留多个数据版本，根据事务或语句快照决定可见性。报表可能在其他事务更新后继续读旧版本。 | 旧版本需要清理；MVCC 是实现机制，不是一个具体隔离级别，也不意味着完全无锁。 | T02 |
| Snapshot Isolation | 一个事务从稳定快照读取，写入冲突按具体规则处理。两个事务可能各自基于旧快照做决定。 | 防止一些读异常仍可能允许 Write Skew；各产品“可重复读”的具体实现需要单独核对。 | T02 |
| Serializability | 已提交并发事务的结果等价于某个串行执行顺序。保护跨行条件时，数据库可能中止一个冲突事务。 | 可能增加等待或重试；它不单独承诺现实时间顺序，后者涉及 strict serializability。 | T04 |
| Dirty Read | 读取另一个事务尚未提交的修改，该修改随后可能回滚。读者可能据此展示从未真正生效的余额。 | PostgreSQL 即使声明 READ UNCOMMITTED 也不允许这种读取；不要靠错误数据库假设演示。 | T01 |
| Read Skew | 多次读取观察到彼此不匹配的时间点。例如转账前读 A、转账后读 B，计算出不存在的总余额。 | 两条 SELECT 分别正确仍可能构成不一致报表；需要合适的共同快照或更强契约。 | T01 |
| Write Skew | 两个事务读相同条件后写不同记录，各自通过却共同违反约束。例如两位值班医生同时下班。 | 只检测同一行的写冲突可能不足；需要明确冲突点、锁或可串行化与事务重试。 | T02 |
| Phantom Read | 同一事务重复范围条件查询，匹配记录集合发生变化，例如另一个事务新增满足金额条件的订单。 | 是否允许取决于数据库和隔离级别；不能只检查原来某一行是否变化。 | T01 |
| Optimistic Locking | 更新时检查读到的版本是否仍有效，例如 UPDATE 带上 version 条件。条件不匹配表示发生竞争。 | 高竞争时重试浪费工作；必须检查受影响行数，不能把零行更新报告成成功。 | T03 |
| Pessimistic Locking | 修改之前先锁住需要保护的资源，例如 SELECT FOR UPDATE 锁库存行。 | 会等待并持有资源，锁范围和持有时间影响吞吐；它不能自动保护未锁定的跨行条件。 | T03 |
| Deadlock | 操作互相持有对方等待的资源，形成等待环。例如两个事务按相反顺序锁两个账户。 | 通常需要终止一个事务打破环；超时不等于死锁证明，统一加锁顺序只能防止相应模式。 | T03 |
| Lock Escalation | 某些数据库将大量细粒度锁升级为更粗粒度锁，以减少锁管理成本。 | 更少的锁可能阻塞更多无关操作；PostgreSQL 不做 SQL Server 式行锁升级。 | T03 |

## 分区与扩展

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| Database Sharding | 将数据分散到多个独立分片，各分片负责部分键。订单可以按租户落到不同数据库实例。 | 跨分片查询、事务、唯一约束与迁移会更复杂；单表分区不一定等于跨实例分片。 | P01 |
| Hash Partitioning | 对分区键哈希后映射到分区，例如 hash(user_id) mod N。 | 通常不保留键顺序，范围查询需散发；简单取模在 N 改变时会移动大量键。 | P01 |
| Range Partitioning | 以连续键区间划分数据，例如按月份分订单。 | 范围裁剪很方便，但递增时间键可能把所有新写入集中到最后一个分区。 | P01 |
| Consistent Hashing | 让节点增减时仅改变一部分键的归属，环与虚拟节点是一种常见实现。 | 虚拟节点改善分布但不消除单个热键；路由变化本身不完成数据迁移。 | P01 |
| Hot Partition | 一个分区承担过高的请求量，先于其他分区饱和。例如最大租户全在一个分区。 | 全集群平均利用率低也可能发生；添加节点未必分担该热点。 | P02 |
| Data Skew | 数据数量、大小或访问频率分布不均。一个用户可能拥有大多数订单，或少数订单被反复读取。 | 存储倾斜与访问倾斜应分别测量；平均值容易隐藏最慢分区。 | P02 |
| Horizontal Scaling | 增加机器或实例承载工作。例如增加 worker 分担独立任务。 | 串行步骤、共享数据库或单个热键可能成为上限；吞吐不必随机器数线性增长。 | P02 |
| Resharding | 改变分片划分或键映射，例如拆分一个过大的键区间。 | 迁移期间需要处理并发更新、旧路由和切换一致性；双写本身不是完整协议。 | P03 |
| Rebalancing | 调整数据或已有分片在节点间的位置，恢复资源均衡。 | 搬迁争用网络和磁盘；迁移速度需与线上负载平衡，不一定改变逻辑分片边界。 | P03 |

## 复制与读取一致性

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| Leader–Follower Replication | 由主节点接受写入，将变更传播给副本。例如写主库、从副本提供报表。 | 主节点故障后的切换和数据保留取决于确认及复制协议；不是复制存在就自动安全选主。 | R01 |
| Read Replicas | 用于分担读取的副本。 | 异步副本可能落后，用户刚创建的订单可能查不到；增加读副本不会直接扩展主库写容量。 | R01 |
| Eventual Consistency | 在没有新更新并满足传播与修复条件时，副本最终收敛到相容状态。 | 没有自动承诺收敛时间，也不保证中途读取顺序；永久故障或缺失修复条件会破坏收敛。 | R02 |
| Strong Consistency | 通常用来表达较强的可见性保证，但术语本身过宽。具体实验应明确是否要求线性一致性等契约。 | 不能用“强一致”三个字替代可检验定义；正常单节点读取不证明故障切换时仍满足契约。 | R02 |
| Consistent Reads | 按明确一致性规则执行读取，可能指同一快照、会话读己之写或线性一致读取。 | 必须结合产品和接口说明，不能把这些不同保证当作同义词。 | R02 |
| Read Repair | 读取时发现副本版本差异并修复过期副本。 | 不被读取的数据可能长期未修复；版本比较和冲突处理规则决定修复是否正确。 | R02 |
| Multi-Leader Replication | 多个节点都接受写入，再相互传播。例如两个地区各自处理本地修改。 | 并发冲突必须有业务可接受的处理规则；简单按时钟覆盖可能丢失更新。 | R03 |
| Geo-Replication | 在不同地理位置保留数据副本，用于就近访问或地域故障恢复。 | 跨区传播增加延迟与成本；它可以采用单主或多主，不天然表示多主。 | R03 |
| Physical Replication | 传播与存储物理结构相关的变更，例如 PostgreSQL 的物理 WAL 流复制。 | 通常约束软件版本和存储格式，灵活筛选业务表的能力有限。 | R04 |
| Logical Replication | 按逻辑数据变更传播，如某表的插入、更新、删除。 | DDL、序列、复制标识与冲突处理有产品限制；不能假定整个数据库对象都会同步。 | R04 |

## 共识与网络分区

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| CAP Theorem | 出现网络分区时，系统无法同时满足特定定义下的线性一致性与可用性。 | 不是日常随意“选两个”；这里可用性是每个到达非故障节点的请求最终获得响应，并非年度 SLA 百分比。 | C01 |
| Quorum | 达成某项操作所需的节点集合或数量。读写集合相交可使读取有机会接触较新版本。 | R+W>N 只说明交集；版本选择、并发写、失败操作和成员变更也会影响一致性。 | C01 |
| Two Generals Problem | 在不可靠通信中，反复确认仍无法建立双方都确定对方已经确定的无限层次共同知识。 | 用来理解最后一条确认丢失的困境；不要将其当作“任何共识算法都不可能”的证明。 | C01 |
| Leader Election | 按协议决定谁在某个任期内负责协调，例如调度器主节点。 | 超时只能产生怀疑；单独选出领导者并不保证日志安全或旧领导不再写资源。 | C02 |
| Split-Brain | 分区等原因让多个节点同时按主角色行动。旧主仍能写存储时可能破坏状态。 | 除角色切换外，还要在资源端拒绝旧拥有者；“我认为我是主”与有效写权限不同。 | C02 |
| Raft Consensus Algorithm | 通过任期、选举、日志匹配和提交规则复制状态机。多数可用并满足相应时序条件时可以推进。 | 持久投票、日志新旧限制及当前任期提交规则不能省略；固定成员写入共识不自动覆盖所有读取和成员变更。 | C03 |

## 分布式协调与事务

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| Distributed Transactions | 一个事务跨多个资源，仍希望满足约定的提交及隔离契约。例如两个数据库共同完成转账。 | 故障下存在不确定结果、阻塞和协调成本；只在每个服务内开事务并不构成整体原子性。 | D03 |
| Two-Phase Commit (2PC) | 协调者先让参与者准备，再通知统一提交或回滚。准备成功必须有可恢复的状态。 | 协调决定不可得时参与者可能保持 in-doubt 并占用资源；持久化恢复协议至关重要。 | D03 |
| Three-Phase Commit (3PC) | 在特定故障与时序假设下增加中间阶段，以减少某些 2PC 阻塞情形。 | 不普遍解决异步网络分区；违反假设时按超时自行决定可能不安全。 | D03 |
| Saga Pattern | 将业务拆成多个本地事务，失败时用业务补偿处理已完成步骤。例如订单取消后退款和释放库存。 | 补偿也会失败，且不是时间倒流；中间状态可见，需要去重、恢复与人工处理边界。 | D04 |
| Distributed Locking | 跨进程协调资源拥有权，常用租约避免永久占锁。 | 旧持有者暂停超过租约后仍可能继续运行；被保护资源需验证 fencing token 等有效性。 | D02 |
| Idempotency | 重复执行在约定观察范围内产生与一次执行相同的效果。例如重复请求键返回同一订单。 | 去重结果与业务写入必须协调持久化；相同键不同载荷需拒绝，过期后保证可能变化。 | D01 |
| Exactly-Once Semantics | 在明确边界内让效果恰好出现一次，例如事务性消费与输出。 | 不表示网络仅发送一次；外部邮件、支付或去重期限之外的重试可能不在保证范围内。 | D01 |

## 数据建模与查询优化

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| Normalization | 按数据依赖组织关系，减少不必要重复与更新异常。例如把客户当前地址放到客户表。 | 查询可能需要连接；历史成交价格不应因追求去重而错误引用商品当前价格。 | Q01 |
| Denormalization | 为特定读取保留冗余数据，例如把客户显示名复制到读取表。 | 需要说明谁维护副本、何时更新以及能容忍多旧；不是无条件性能优化。 | Q01 |
| Secondary Index | 主访问路径之外的索引，例如按用户 ID 找订单。 | 占空间并增加写入维护；索引命中后可能仍需回表，不是索引越多越好。 | Q02 |
| Index-Only Scan | 在满足条件时仅凭索引提供查询所需内容，减少访问表的数据页。 | PostgreSQL 还受可见性映射影响；索引包含所有列也可能仍发生 heap fetch。 | Q02 |
| Query Planner | 为查询选择扫描、连接、排序等执行步骤。 | 计划好坏依赖统计与可选路径；同一 SQL 在不同数据分布下可能选择不同计划。 | Q03 |
| Cost-Based Query Optimization | 用成本模型比较候选执行计划，例如估算索引扫描与顺序扫描的代价。 | 成本不是精确墙钟时间；行数估错、字段相关或数据倾斜会导致错误选择。 | Q03 |
| Materialized Views | 将查询结果实际保存，减少重复聚合计算。 | 需要刷新，结果可能落后；刷新锁行为和增量支持取决于产品。 | Q04 |
| Caching | 保留可复用结果以降低重复访问成本，例如缓存热门商品详情。 | 失效、过期、并发回填和内存上限决定可靠性；缓存不是数据库一致性的自动延伸。 | Q04 |

## 流量与资源管理

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| Connection Pooling | 复用有限连接，避免每个请求都建立昂贵连接。 | 池满时仍需等待、拒绝或超时；增大池可能压垮数据库而非提高吞吐。 | F01 |
| Connection Multiplexing | 多个逻辑使用者共享较少的物理连接，具体按协议或事务边界复用。 | 不能任意交错数据库会话状态；代理事务池与 HTTP/2 多流是不同实现语境。 | F01 |
| Database Connection Leaks | 请求结束后未归还或关闭连接，逐渐耗尽连接资源。 | 普通成功路径可能看不出，异常和取消路径更容易泄漏；重启只暂时缓解。 | F01 |
| Load Balancing | 将请求分配到多个处理者，例如轮询或按在途工作量选择 worker。 | 请求成本和节点速度不均时，均分请求数并不等于均分负载。 | F02 |
| Rate Limiting | 限制时间窗口内或令牌预算允许的请求量。 | 需定义突发量、作用域与分布式计数语义；平均速率限制不直接约束在途并发。 | F02 |
| Backpressure | 消费能力不足时，将等待或拒绝信号传回生产者，限制积压。 | 只给队列设上限却在上游继续无限缓存，不能形成端到端背压。 | F02 |
| Circuit Breaker | 依赖持续失败时暂时快速拒绝调用，并通过有限探测判断恢复。 | 误判、探测并发和状态范围会影响恢复；它不代替超时、限流或幂等。 | F03 |
| Retry Storm | 大量请求或多层服务同时重试，放大原有故障。例如三层各重试三次造成乘法增长。 | 需要总截止时间、重试预算和退避；仅增加重试次数可能使恢复更慢。 | F03 |
| Thundering Herd Problem | 大批等待者在同一事件后同时行动，例如热门缓存同时过期后集中回源。 | 请求合并需处理填充者失败；单进程合并无法自动消除跨节点同时回源。 | F04 |

## 可用性与恢复

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| High Availability (HA) | 通过冗余、检测、切换和运维措施降低服务中断，按明确服务指标衡量。 | 数据库在线不等于业务可用；共享电源、网络或配置可能造成共同故障。 | A03 |
| Failover | 当前服务实例失效后把职责转移给另一个实例。 | 错误检测可能切换过早；必须处理旧主隔离、客户端连接和副本落后造成的数据损失。 | A03 |
| Checkpointing | 保存与明确执行或日志位置对应的状态，从而减少恢复需要重放的工作。 | 先删日志后发布有效快照会失去恢复链；不同系统的 checkpoint 契约不完全相同。 | A02 |
| Backups vs. Point-in-Time Recovery | 备份保存某时刻的恢复基础；PITR 通常结合基础备份与连续日志恢复到之后的指定位置。 | 日志缺口会中断恢复链，必须实际演练；复制会传播误删，不能替代备份。 | A01 |

## 数据流与应用架构

| 概念 | 实际含义与例子 | 代价或失败边界 | 模块 |
| --- | --- | --- | --- |
| Change Data Capture (CDC) | 捕获源数据库的已提交变更，驱动下游同步或投影。 | 初始快照与增量衔接、重复、顺序及删除都需处理；不是自动的跨系统事务。 | E01 |
| Schema Evolution | 在新旧程序并存时逐步改变表或事件结构，例如先增加可选字段、回填，再收紧约束。 | 兼容性有方向和生命周期；旧代码退出前删除字段可能中断服务，过渡逻辑最终需要清理。 | E02 |
| Event Sourcing | 把领域事件序列作为状态事实来源，通过重放得到当前状态。 | 事件版本与历史语义长期存在；重建状态不应重新触发扣款或发送邮件。 | E03 |
| Denormalized Read Models | 从事实来源维护面向特定查询的冗余投影，例如订单列表附带客户信息。 | 投影可能落后，需支持去重和重建；投影错误不应污染事实来源。 | E03 |
| Data Warehouse | 面向跨来源历史分析组织数据与计算，例如长期销售趋势与客户分群。 | 摄取、迟到修正和口径一致性有成本；分析库存在不等于所有报表数据实时。 | E04 |
| Federation | 通过统一查询入口访问多个独立数据源，尽量把过滤计算下推到源。 | 源故障、网络读取量和不同更新时间影响结果；默认不提供跨源一致快照。 | E04 |
