# T01 模块计划

读者会 Python 与 SQL；目标是在真实 PostgreSQL 上用明确事件顺序验证事务原子性及隔离可见性。场景为账户转账与余额报表；模型压缩为两条账户记录、一个额外插入和两个连接，不实现数据库或支付系统。

供给事实：路线指定 PostgreSQL 和 v0-v4；实施假设：整数金额、独立测试实例、同步驱动。已提交转账总额必须保持 200，所有观察标注提交位置；v3 新账户存入 50，因此总额改变是预期输入，不再套用转账总额不变量。

依赖顺序：v0 原子提交 → v1 未提交可见性 → v2 不同语句快照 → v3 谓词集合 → v4 ACID 证据边界。

1. v0：写失败注入与回滚教程，验收 70/130、失败 100/100、非法请求无变更；代码为 transfer.py/schema.sql。
2. v1：在未提交扣款之间安排第二连接读取，验收 RC/RU 均读 100；代码增添 observations.py。
3. v2：在报表两条读取之间提交转账，验收 RC 230、RR 200；保留 v1 行为。
4. v3：在重复范围读取之间提交插入，验收 RC 2→3、RR 2→2；新增连接能读到 3。
5. v4：添加约束失败实验与重新连接读取，整理证据对应关系；不新增事务框架。

每个版本先写具体 plan.md，再逐步编写 tutorial.md，提供完整当前代码检查点；测试既运行源码也从正文抽取完整代码独立重放。独立 reviewer 检查教学连续性、真实 SQL 行为、故障与清理边界，作者修复后重测。本轮不提交 Git。

Helper 边界：transfer 是真实调用入口；main 只建立并清理实验 schema；观察函数返回读取值而不隐式初始化表。pytest fixture 因每个测试需独立初始数据而建立 schema，连接关闭后只删除自己创建的 schema。

审查风险：autocommit 默认值掩盖部分提交；RR 在首条查询建立快照而非连接时；把约束等同所有业务一致性；把重连读取等同崩溃恢复。各版计划将这些风险落到具体检查。
