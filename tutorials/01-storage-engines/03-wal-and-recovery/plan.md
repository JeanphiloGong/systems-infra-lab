# S03 写作计划

读者会文件读写，理解转账总额不应凭空变化。实际场景是服务器返回成功后突然退出；压缩模型为两个账户、赋值操作、追加日志和提交帧。核心不变量：确认提交的事务可恢复，未提交事务不成为恢复后的可见结果，重复恢复不能重复扣款。

约定 Python 3.12+、本地 POSIX 文件系统、单写者、日志不压缩不截断。进程退出实验不证明断电可靠性；fsync 的真实保障依赖文件系统与设备。日志损坏与合法截断尾分开处理：完整帧校验不符必须报错，不跳过后继续读取。

1. v0：直接覆盖 JSON，扣款后子进程退出；证明总额减少。完整目标 baseline.py，验收退出码 73 与 90/100。规模 S，前置文件 I/O。
2. v1：追加 JSON 操作没有自带可靠边界；定义长度、负载和 CRC32，识别完整帧与未完成尾帧。完整目标 framing.py，验收每字节截断及完整帧损坏。规模 M，依赖 v0。
3. v2：先写操作日志后改数据，进程退出后重放赋值可重复，但仅凭操作日志不能判断是否提交；明确暴露 pending 事务。目标 prepared.py，验收日志在数据之前与未提交分类。规模 M，依赖 v1。
4. v3：增加提交帧，按事务收集操作并只重放已提交组；恢复自初始状态，不信任部分数据文件。目标 store.py，验收多操作全有全无与重复恢复。规模 M，依赖 v2。
5. v4：把写日志、flush、fsync、返回成功的顺序形成可检查轨迹；处理新日志目录项持久化，明确错误时不得返回确认。目标 store.py，验收顺序与失败注入。规模 M，依赖 v3。
6. v5：每个明确写入边界使用子进程退出，再启动恢复；验证未确认可能提交但不部分提交，已确认必须恢复。目标 crash_worker.py 与完整 store.py；验收崩溃矩阵及重复恢复。规模 L，依赖 v4。

每个版本先完成计划与最小失败实验，再写正文完整代码和打印检查，独立审核并修复。辅助函数只随编码边界、事务缓冲和持久化顺序需要引入；不构建通用存储框架。检查点提交策略：本轮不提交 Git。
