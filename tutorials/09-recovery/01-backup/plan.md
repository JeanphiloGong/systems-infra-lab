# A01：备份与目标时间恢复的编写计划

状态：补齐模块计划，待独立审核；已通过的 PITR 实验不是全部路线图要求的证明。
前置 S03 的提交/WAL 边界、R04 的物理复制，以及专用 PostgreSQL 和 Docker 环境。

## 场景、模型与契约

操作者误删一条已提交订单，需要在不覆盖当前数据库的情况下取回误删前的数据。
现有实验使用 `accounts(id,balance)` 的两行 1:100、2:100，压缩业务数据而保留
误删、备份后写入、日志归档、第二恢复实例和目标时间。核心对象只有备份、WAL 段、
恢复目标和恢复结果。文件存在或恢复端口打开均不能代替业务结果验收。

不变量：成功的目标恢复必须包含删除前的第二行，排除目标之后的写入；缺少必要
日志必须失败，不能接受部分恢复。所有故障注入只作用于专用数据库或归档副本。
副本能同步误删，不是历史恢复点。RPO/RTO 必须说明测量起止，不能返回常量冒充观测。

## 按依赖编写与修订

1. **v0：证明逻辑备份可恢复。** 从两行账户和主键约束开始，plain SQL dump 后
   恢复到独立数据库。检查表、行值、行数和重复主键拒绝；源库保持可查询。
   当前 `v0.py` 在同一数据库 DROP/restore，只证明往返，还需补独立恢复目标和约束验证。
   冻结完整脚本与恢复前后结果，下一步加入备份后的写入。
2. **v1：观察备份时间边界。** custom dump 后插入 `(3,50)`，恢复结果只能有两条
   备份内记录。解释这是备份截止时点的结果，不是恢复工具漏行；后续订单需要连续 WAL。
   现有输出 `rows_at_backup=2`、`post_backup_row_excluded=True` 应来自行查询。
   与 v0 同样保留源库和独立目标，避免用原地回滚混淆灾难恢复和回档。
3. **v2：建立物理备份和归档链。** 对照路线图，此版应执行基础备份、确认完成边界，
   等待实际 WAL 段归档并验证从备份起点到恢复所需位置的连续性。已有 `common.py`
   的 `create_base_backup`/`wait_archive` 可作为实现依据，但需解释先后顺序和失败条件。
   当前 v2 只截断逻辑 dump，物理备份在 v3 才首次执行：版本承接尚需修订。
   保留截断反例的验收价值，把它放入 v4 故障实验，而不是删除原范围要求。
4. **v3：恢复误删之前。** 基础备份后取得数据库目标时间，再删 ID 2、插入 ID 3。
   归档到位后启动独立恢复容器，等待目标暂停并核对 `1:100,2:100`；源库此时为
   `1:100,3:300`。解释目标时间、提交顺序及暂停条件；不能只等 `pg_isready`。
   冻结目标恢复闭环，仍缺断链失败和时间/损失窗口测量。
5. **v4：证明失败可识别。** 复制归档后删必要 WAL，要求恢复报告目标未到达；
   损坏逻辑备份副本也必须报告失败。使用 monotonic clock 测量恢复尝试耗时，并
   用源/目标已提交操作的时间与集合明确恢复点之后损失的范围。现有 v4 已验证
   缺段报错，但没有耗时或损失窗口输出；不能用五秒 timeout 当实测恢复时间。
   最后提供完整源码、故障结果与清理命令，不泛化为生产恢复 SLA。

每版写作顺序为具体失败轨迹、前版缺口、一项机制改动、立即运行、完整当前代码、
尚缺能力。版本任务继续细化到各 `vN/plan.md`，本文件不代替版本任务。
