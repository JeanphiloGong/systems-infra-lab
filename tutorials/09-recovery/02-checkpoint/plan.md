# A02：从完整日志恢复到可回收的检查点

状态：实现计划，尚无已验收版本。原范围见 `docs/roadmap.md` A02。
读者已完成 S03，理解提交记录、CRC、fsync 与进程崩溃的区别。
目标是亲手证明：快照与日志位置必须一致，而安全回收取决于最旧保留快照，
不只是最新快照。采用暂停写入的单写者实验，不引入后台线程或通用存储接口。

## 场景和模型

账户余额服务不断提交转账，虽然当前状态只有两个余额，重启仍需读取全部历史。
输入是连续编号的已提交事务；输出是恢复后的余额、恢复读取字节数、重放事务数。
沿用 S03 的 `alice=100,bob=100`，事务包含两个 set 和一个 commit；
使用 `labs/storage/wal/framing.py` 已验证的长度与 CRC 编码。
不修改 S03，不为其 Store 添加兼容包装层。

为让完整日志段能被直接回收，A02 将每个完整事务存为一个不可变日志段。
这是公开的教学格式变化：编号代表完整事务位置，不是 S03 字节偏移或 PostgreSQL LSN。
每段仍保留 S03 的 set/commit 记录边界。写者 fsync 临时段，再重命名并 fsync 目录，
最后确认提交。临时段不算提交；目录同步前的进程崩溃不构成断电证明。
这种一事务一文件格式便于验证保留范围，但不适合高吞吐生产负载。

最小模型只有已提交日志段、账户状态、快照、发布清单和恢复位置。
核心不变量：

- 状态和位置对应同一完整事务前缀；绝不把位置 N+1 的状态标为 N。
- 在单写者暂停期间取快照；确认提交的后续日志必须从下一连续位置重放。
- 清单只引用完整、持久化并通过校验的快照。
- 删除日志前持久化发布清单；保留上一快照时保留从它之后开始的全部日志。
- 快照损坏可以回退；恢复所需日志缺失或 CRC 错误必须失败，不能返回部分状态。
- 恢复不修改输入文件；重复恢复结果一致，不能重复转账。

## 写作任务

各任务的 checkpoint commit 均为 no：当前会话不自动创建提交或 tag。
每个版本的最后一步给出完整源码、依赖源码、命令和预期输出；前面的局部修改
标明 patch。旧版通过正文提取在临时目录独立运行，不导入最新 A02 实现。

### 1. v0：先量出完整重放的代价

前置：S03 的记录格式和提交语义；无快照前置。
文档目标：`v0/tutorial.md`，代码目标：`labs/recovery/checkpoint/store.py`。
预计规模：初始化与一笔提交、重启重放、增长实验三个教学步骤。

从调用者执行一笔转账后重启开始，提供编号日志段和完整提交记录。
固定种子生成 10、100、1000 笔转账，最终余额由内存参考序列独立计算。
每次恢复统计实际打开的段数、读取字节和解码的事务数，不把数字直接设为输入规模。
读取顺序必须按编号；拒绝中间缺段和损坏记录，忽略未发布的临时文件。
验收：三个规模结果均与参考状态一致，读取量随历史增长；空日志恢复初始余额。
验证命令目标：`uv run pytest tests/recovery/checkpoint -q`。
冻结：提交与完整重放工作正常；下一缺口是大量历史需要重复解码。

### 2. v1：用同一位置的快照跳过前缀

前置：v0 正文和实验通过。
文档目标：`v1/tutorial.md`；继续修改同一 store，增加 snapshot/recover 路径。
预计规模：保存状态与位置、从下一位置读取、对照实验三个教学步骤。

保持所有旧段不删，写入 100 笔后暂停，保存第 100 笔对应状态和位置。
再提交 5 笔，以快照加尾部重放恢复，与无快照的 105 笔重放对比。
快照使用明确版本号和 CRC；位置不能从文件名猜测，也不能读取状态之后再查询位置。
验收：两条恢复路径余额相同；快照路径只解码 5 个事务而非 105 个。
覆盖零位置、刚好最后位置、快照后无新增和快照后一次更新。
冻结：恢复工作量变小，但旧文件仍占空间，快照发布尚需定义崩溃顺序。

### 3. v2：发布之后才能删除日志

前置：v1；读者复习 S03 的文件同步顺序。
文档目标：`v2/tutorial.md`；代码仍为 store，新增仅用于实验的 crash_worker.py。
预计规模：错误顺序反例、原子发布、真实退出重启三个教学步骤。

先在临时实例演示先删前缀再发布快照导致恢复缺段。
改为快照临时文件写入/fsync、重命名/目录 fsync、清单写入/fsync、
清单原子替换/目录 fsync、最后回收无用日志并同步目录。
清单发布是新恢复入口；之前的清单和段必须仍足够恢复。
事件钩子只用于确定性故障注入，不成为生产接口抽象。

验收：在快照发布前后、清单替换前后、第一段删除后分别由子进程 `os._exit`
退出，父进程再启动新进程读取相同目录，确认全部已确认事务仍存在。
不能在同一对象上再调用 recover 代替重启；每条路径记录真实退出码和最终余额。
冻结：可以安全回收；下一缺口是唯一有效快照损坏后没有恢复起点。

### 4. v3：备用快照需要自己的日志尾部

前置：v2 的持久化和故障边界实验。
文档目标：`v3/tutorial.md`；最终代码 checkpoint 包含 store、实验和完整依赖。
预计规模：错误回收反例、双代保留、故障全集四个教学步骤。

取位置 10、20 的两个快照，再提交到 25。
先展示只保留 21–25 日志时，损坏位置 20 快照不能从位置 10 恢复。
修改回收下界为最旧保留快照的位置；保留 11–25，损坏最新快照后从旧快照
恢复到 25。恢复统计证明实际用了旧快照和 15 个事务，而非未声明的完整备份。
清单记录两代；写第三代并发布后才回收第一代及相应日志。

验收：最新快照正常、最新损坏回退、两代均损坏拒绝、备用所需日志缺失拒绝、
第三代轮转前后崩溃、新事务编号不回退，以及恢复两次结果一致。
最终重跑 v0–v3 正文提取实验，独立审核后才更新共享进度与教程入口。
冻结：满足暂停写者、有界恢复、双代回退；不停写快照和完整 ARIES 不在本模块内。

## 辅助函数边界与核对

恢复函数只读取磁盘，返回余额、已恢复位置和实际工作量；发布函数改变文件集合，
必须把发布顺序放在正文里解释。CRC 使用 S03 已有编码，不另建校验框架。
暂不冻结类布局；只有写作步骤实际需要时才引入 helper。

故障矩阵对应上述任务：v0 空历史/缺段/损坏；v1 位置边界/尾部覆盖；
v2 发布前后真实退出；v3 代际轮转/快照损坏/回退日志保留。
测试必须检验具体状态和文件保留范围，不能仅断言打印了成功文本。
时间可作为辅助实测，确定性验收使用事务数和字节数；不要求某台机器快几倍。

审核重点：是否把内存状态当作磁盘恢复；是否取错快照前缀；是否在发布前删除日志；
是否让备用快照引用已回收日志；是否拿进程退出证明断电安全；是否隐式依赖仓库最新源码。
